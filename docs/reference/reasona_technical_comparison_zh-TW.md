# Reasona AI：Agent Framework 與 LLM 後端技術比較

**資料快照：2026-10-03。**本報告依官方 GitHub repositories、README、文件、license 與 model cards 整理，共列 27 個 Agent／orchestration 框架及 11 個推論軟體或模型服務介面。每列附可直達來源與查閱日期；GitHub 活躍度以官方 API 的最近推送日期、封存狀態及維護者明示狀態為訊號，不以 stars 當成熟度證明。只使用公開免費資料；未登入、註冊、購買、部署或執行外部程式。

先分清三種「開放」：**框架／推論軟體的原始碼授權**、**模型權重授權**、以及**託管 API 的服務條款**互不相同。可用開源 server 載入某模型，不代表模型權重也採寬鬆開源授權；OpenAI-compatible 也只表示部分 API 格式相似，不保證所有參數、工具呼叫或 JSON Schema 行為完全一致。

## 1. Agent 與 orchestration frameworks

### 框架比較如何解讀

若 Reasona AI 的網站原型要讓使用者審核 agent 動作，優先挑有**明確暫停／批准語義**的方案（例如 LangGraph、PydanticAI、MAF、ADK、CrewAI、Mastra），而不是只看它是否標示「agent」。若主要價值是私有知識問答，LlamaIndex、Haystack 或 Dify 的 RAG 能力更直接；若資料安全或租戶隔離是核心，則要把外部向量庫、記憶保存、日誌與 API 傳送路徑納入設計。這些是依各 repo 公開功能的架構判斷，不是同資料集的性能 benchmark。

維護訊號中特別值得排除或限制的案例：AutoGen 已進 maintenance mode；Flowise、TaskWeaver 已封存；Rasa OSS 已進 maintenance mode；Semantic Kernel 有明確 successor；BeeAI 的 README 不承諾持續維護；Letta 已移轉程式碼且舊 API retired。它們仍可用於既有系統或比較，但不宜因人氣或歷史知名度而直接視為新案的長期基底。

## 3. 小黎可選的 MVP 組合

目前沒有 Reasona AI 的產品需求文件、預計流量、資料敏感度或硬體規格，因此下列依「網站原型需提供後端 API」假設提出，供另一位 Agent 按產品邊界取捨；不是同條件 benchmark，也不代表哪個絕對最佳。

|方向|組合|優點與代價|較合適的驗證目標|
|---|---|---|---|
|**快速型別化單 Agent**|**PydanticAI + Gemini API（原生 Gemini SDK 或 OpenAI-compatible endpoint）+ 小型 FastAPI 後端**|型別輸入/輸出、tool approval 和 server streaming 容易做成網站 API；不用維護 GPU。需支付或遵守當時配額；免費層資料條款不適合敏感內容；跨 provider 相容仍要做測試。|先驗證對話體驗、少量安全的工具呼叫與結構化回覆；複雜長任務先不導入多代理。|
|**需要流程控制與人審**|**LangGraph + OpenAI、Anthropic 或 Gemini 商業 API + PostgreSQL checkpointer**|圖狀態、暫停審核、持久執行讓網站端較容易落實「提出計畫—等待使用者批准—繼續」；可切換 API，但 API 費、資料條款、檢查點與觀測維運需負責。|驗證長流程、可中止/重試、人工批准，以及不同模型 API 的 tool/JSON 相容測試。|
|**自託管／資料留本機**|**LangGraph + Ollama（原型）或 vLLM（有 GPU 的較高吞吐服務）+ Apache-2.0 Qwen3-8B + PostgreSQL/pgvector**|若全部在自管環境，prompt 不需傳到外部模型 API；Qwen3-8B model card 標 Apache-2.0。代價是硬體、下載儲存、GPU 容量、升級與安全運維；本機模型的工具呼叫/輸出 schema 需實測。|確認資料不得出境或成本需可預測，且團隊有可用硬體/部署能力；不適合無 GPU、要求最少運維或尚未評估本機模型品質的情境。|

若 Reasona AI 只是單頁網站原型、尚未定義租戶或人審流程，可先以第一組建立最小 server API；若網站涉及多個使用者、工具會造成外部副作用，第二組可較直接驗證批准及可恢復性。若想用視覺化 Dify 加快內部 demo，需先確認是否單租戶、不得改其 console/app 標誌；官方 Dify license 對多租戶部署要求書面許可。這是授權與產品拓樸限制，不是性能問題。

## 4. 原型整合時的必要驗證

1. **API 合約測試**：至少驗證 tool schema、tool choice 行為、串流事件格式、structured output 的 JSON Schema 子集、錯誤/重試與模型名稱。Ollama 明確不支援 `tool_choice` 等欄位；其他相容端也應實測，避免只靠 OpenAI SDK 能連線便推定全相容。
2. **資料流與租戶隔離**：將使用者輸入、知識文件、對話記憶、執行軌跡及錯誤 log 分別記錄其保存位置與刪除期。使用路由 gateway 時還要確認 fallback 後會送往哪個 provider。
3. **工具批准與安全**：在 UI/後端以白名單和最小權限限制工具；寫入、寄送、刪除或付款等副作用在伺服器端另設明確批准與冪等控制。Agent framework 的「HITL」不自動等同權限安全機制。
4. **費用與容量**：託管 API 依使用量和產品層級計費，價格與免費額度會變；自託管則把模型費換成硬體、電力、維運與容量成本。模型能力、數據政策與延遲應用 Reasona 自己的測試集比較，不以 marketing claims 或 stars 代替實測。
